# C3 cloud compute

[C3](https://cthree.cloud) runs swarm benchmarks on remote cloud hardware. Use
it when you do not want to install Docker or do not have the hardware required
for local benchmarking. Set an agent's `compute` field to `"c3"`; use
`"local"` for local Docker instead.

The setup UI handles the normal C3 configuration flow. The instructions below
are for terminal setup, manual configuration, and troubleshooting.

## Install and authenticate the C3 CLI

On macOS or Linux:

```bash
curl -fsSL https://cthree.cloud/install.sh | sh
```

Then authenticate using either an existing login session:

```bash
c3 login
```

Or create an API key and export it:

```bash
c3 apikey create tig-swarm
export C3_API_KEY=c3_...
```

### Windows

The shell installer above is for macOS and Linux. In PowerShell:

```powershell
# Create an install folder.
$dir = "$env:LOCALAPPDATA\Programs\c3"
New-Item -ItemType Directory -Force -Path $dir | Out-Null

# Download the Windows binary.
curl.exe -fsSL "https://cthree.cloud/releases/latest/c3-windows-amd64.exe" -o "$dir\c3.exe"

# Add the folder permanently to the current user's PATH.
$userPath = [System.Environment]::GetEnvironmentVariable("Path", "User")
if (($userPath -split ';') -notcontains $dir) {
  [System.Environment]::SetEnvironmentVariable("Path", "$userPath;$dir", "User")
}

# Also make it available in this PowerShell window.
$env:Path = "$env:Path;$dir"

c3 --version
```

Other open terminals will not see the updated `PATH` until restarted. The
download above is for most x86-64 Windows computers; on an ARM Windows computer,
use `c3-windows-arm64.exe` instead. To update the CLI later, download the binary
again and overwrite the existing `c3.exe`.

Authenticate with `c3 login`, or create a key with
`c3 apikey create tig-swarm` and set it for the current PowerShell session:

```powershell
$env:C3_API_KEY="c3_..."
```

## Manual fleet configuration

These fields can be set in `fleet.config.json` when the setup UI defaults are
not sufficient:

| key | purpose |
| --- | --- |
| `compute` | `"c3"` for C3 cloud hardware or `"local"` for local Docker. If omitted, it falls back to `"local"`. |
| `c3_hardware` | Hardware selector. `"auto"` selects an appropriate CPU or GPU profile; pin an exact profile only when needed. |
| `c3_time` | Per-job wall-time limit. The default is `02:00:00`. |
| `c3_provider` | Optional C3 backend passed to `c3 deploy -p`. |
| `c3_api_key` | Optional per-agent raw API key. If omitted, the agent inherits the fleet-level `c3_api_key`, then `C3_API_KEY`, then the `c3 login` session. |
| `env_image` | Docker Hub image for the job. Defaults to `rust:1-bookworm` for CPU or `nvidia/cuda:12.6.3-cudnn-devel-ubuntu24.04` for GPU. Use `env_cpu` or `env_gpu` to configure them separately. |

## How remote benchmark jobs run

All agents using the same C3 key share the subscription's pool of concurrent
jobs. The fleet reads the subscription's current concurrency limit at launch,
so changing plans does not require a fleet configuration change.

Each benchmark proceeds in three stages:

1. **Split.** The benchmark's nonces are divided into balanced shards, up to the
   number of available concurrent-job slots.
2. **Queue.** Shards share a first-come, first-served fleet-wide slot pool. When
   all slots are occupied, later work waits until a slot becomes available.
3. **Merge.** Completed shard results are combined and scored once, producing
   the same aggregate result as an unsharded benchmark.

With one active agent, its shards can use the whole pool. With multiple agents,
their shards share the pool and may wait behind earlier submissions. The fleet
does not submit more simultaneous jobs than the subscription permits.

For implementation details and trust-boundary considerations, see
[Architecture](./ARCHITECTURE.md#local-vs-c3-compute).
